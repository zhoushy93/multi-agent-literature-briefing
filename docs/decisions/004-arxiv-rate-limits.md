# 004 — arXiv 限流：406 的含义与应对

状态：**已决定**
日期：2026-09-18
关联：`AGENTS.md` §7、`docs/SPEC.md` §3.1 G2、`TASK.md` Step 4

---

## 背景

运行时报 `arxiv returned HTTP 406 Not Acceptable`，且一次运行的 6 个查询**全部**失败。排查过程与结论：

| 观察 | 结论 |
| --- | --- |
| 单个 `curl` 请求（各种 User-Agent，含本项目的） | 一律 200 → **不是 User-Agent 的问题** |
| 单个 `httpx` 请求 | 时而 200、时而 406 |
| 6 个查询并发 | 全部 406（与客户端实现无关，curl 并发同样会触发） |
| 触发后暂停 30–60 秒再单发 | 恢复 200 |
| 持续重试（4 次 × 6 查询，约 70 秒） | 仍是 406，且**封禁被延长** |

即：**406 是 arXiv 侧的限流响应**（它用 406 而不是 429 表达"你请求太多了"），针对来源 IP、按滚动窗口计算。这与 arXiv API 的使用约定一致：单客户端约每 3 秒不超过一次请求。

## 决定

在数据源层实现"礼貌访问"，而不是在被限流后失败或死循环重试：

1. **请求间隔**：同一 source 的请求串行化，默认至少间隔 3 秒（`BRIEFING_SOURCE_MIN_INTERVAL_S`）。
2. **共享冷却**：一旦收到 406/429，把冷却截止时间记在 source 上（20s → 40s → 80s，上限 120s），**所有并发查询一起等待**，而不是各自重试把封禁续命（这是最初实现的真实缺陷：6 个任务各重试 4 次 = 在封禁窗口里又打了 24 次）。
3. **有界重试**：网络错误与 406/429/5xx 重试，最多 `BRIEFING_SOURCE_MAX_ATTEMPTS`（默认 4）次；`Retry-After` 优先。4xx（非 406/429）不重试。
4. **错误可操作**：耗尽重试后抛出的信息明确说明"这是限流，请等待几分钟，并去掉 `--no-cache` 以复用缓存"。
5. **多源降级**：`AGENTS.md` §7 要求"单一数据源不得拖垮整次运行"。因此新增 **OpenAlex**（免费、无需 key，`sources/openalex.py`）作为默认备用源：某查询在自己的源上失败时，会以纯文本形式（`to_plain_query` 去掉 `all:`/`abs:` 等字段前缀与布尔算子）重试到其它已配置源，并记入 `dropped["source_fallback"]`。

## 实测结果（2026-09-18）

在 arXiv 对本机 IP 持续返回 406 的情况下：

| 场景 | 结果 |
| --- | --- |
| 检索层单独验证 | arXiv 0 篇 → OpenAlex 80 篇，`source_fallback: 2` |
| 完整真实运行 | **status `ok`**：候选 298（全部来自 OpenAlex）→ 去重/截断 40 → 入选 5 篇；9 次模型调用；12 页 PDF；验证通过、无需修订 |

即：arXiv 被限流不再影响产出，只是候选来源换成 OpenAlex（`papers.json` 的 `origin` 会如实标注）。

## 追加修正（同日）：限流必须熔断

用户真实运行时发现：虽能降级，但**每个查询仍各自重试 4 次、每次冷却 20–120 秒**，一轮白等十几分钟，且持续刺激封禁。迭代三次才修到位：

| 迭代 | 实测请求数 | 原因 |
| --- | --- | --- |
| 1 | 12 | 熔断状态只在 `_fetch` 循环顶部检查，**并发查询早已越过该检查** |
| 2 | 4 | 预算扣减压在请求返回**之后、锁之外**，三个并发查询发出第一次请求时都还看到"预算=2" |
| 3（最终） | **2** | 扣减移入锁内（观察到响应的地方）；`_request` 在锁内再检查一次熔断状态 |

最终行为（真实网络实测，零模型调用）：3 个 arXiv 查询 + 2 个 OpenAlex 查询 → **arXiv 仅 2 次请求、8.7 秒**、候选 100 篇全部来自 OpenAlex、`dropped = {source_fallback: 3, source_rate_limited: 1}`。

代价对比：修复前每个被限流的查询最多花 4 次请求 + 140 秒冷却；现在整轮最多 2 次请求、约 5 秒即放弃并交给备用源。

## 后果与使用建议

- **重复运行请用缓存**（默认开启）。`--no-cache` 每次都真实抓取 6 次，是触发限流的主要途径；它应当用于"必须刷新"的场景，而不是日常重复运行。
- 一次正常运行只发 6 个请求（每个查询一个），在 3 秒间隔下约 18 秒，属于礼貌范围。
- 冷却期内运行会明显变慢（可能 2–4 分钟）但不至于全盘失败；这与"宁可慢也不失败"的取向一致。
- 若被长时间封禁（本文件记录过一次超过 7 分钟仍未恢复的情况），只能等待，或改用其他网络出口。

## 验证

- 单元测试（respx，无网络）：406 → 重试 → 成功的路径、共享冷却、`Retry-After`、持久 406 的报错文案、4xx 不重试。
- 真实网络：限流解除后单发请求 200；修复前后对照见上文表格。
